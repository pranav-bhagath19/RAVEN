# RAVEN Agent Architecture Specification

## 1. Overview & Agent Boundaries

RAVEN uses a focused multi-agent architecture comprising **exactly three specialized AI agents**. 

Agents operate strictly within bounded semantic reasoning roles. They do **not** execute direct side-effects, alter monetary figures, or bypass policy checks. All actions generated by agents are submitted as candidate proposals to the **Deterministic Policy Engine**.

```
                           ┌──────────────────────────┐
                           │ Root Cause Analyst Agent │
                           └────────────┬─────────────┘
                                        │ Diagnosis & Context
                                        ▼
                           ┌──────────────────────────┐
                           │ Recovery Planner Agent   │
                           └────────────┬─────────────┘
                                        │ Candidate Action Proposal
                                        ▼
                          [ Deterministic Policy Engine ]
                                        │ Approved Action + Token
                                        ▼
                           ┌──────────────────────────┐
                           │ Verification Agent       │
                           └──────────────────────────┘
```

## 2. Comprehensive AI Failure Handling Strategy

### Fundamental Safety Principle
> **AI failure must never automatically result in an unsafe financial side effect.**

### Safety Fallback Flow
$$\text{AI Failure} \rightarrow \text{Validation Failure / Retry / Fallback} \rightarrow \text{No Side Effect} \rightarrow \text{Human Escalation (When Required)}$$

## 3. Explicit Failure Modes & Mitigations

| Failure Mode | Description | System Response / Mitigation |
| :--- | :--- | :--- |
| **Hallucinated Evidence** | Agent references event IDs or facts not in state snapshot. | Validation parser drops hallucinated claims. Re-prompts agent or sets confidence to 0.0. |
| **Unsupported Claims** | Reasoning summary contradicts underlying gateway error code. | Validator checks claim alignment against gateway error taxonomy. Rejects output if unaligned. |
| **Invalid Tool Arguments** | Agent generates tool parameters violating schema (e.g. negative amount, bad URI). | Schema validation fails at tool boundary. Execution aborted without side-effect. |
| **Malformed Structured Output** | LLM output fails JSON/Pydantic parsing. | Retry parser with strict schema prompt (max 2 retries). If still malformed, abort with `MALFORMED_OUTPUT_FALLBACK`. |
| **Conflicting Evidence** | Telemetry logs show both success and failure signals concurrently. | Agent sets `confidence < 0.50` and outputs `AMBIGUOUS_EVIDENCE_ESCALATE`. |
| **Low Confidence** | Agent output confidence score falls below required threshold (`< 0.75`). | Policy engine blocks autonomous action and routes to human ops queue. |
| **Tool Timeout / Failure** | Read tool call times out or throws underlying gateway/database exception. | Catch exception at tool wrapper. Log error, halt agent cycle, retry or escalate. |
| **Model Timeout / Failure** | LLM API call times out or returns HTTP 5xx / 429 rate limit. | Catch exception in LLM adapter. Fall back to Rule-Based Recovery baseline (`Baseline 3`). |
| **Policy Conflict** | Agent proposes action violating merchant policy (e.g., retrying captured payment). | Policy Engine blocks proposal (`BLOCKED`). DecisionTrace logs policy block. Zero side-effects. |
| **Unavailable Data** | Essential payment telemetry or customer profile is missing. | Agent flags missing data dependency and requests human review. |

## 4. Agent Trio Specifications

### 4.1 Agent 1: Root Cause Analyst Agent
- **Purpose**: Diagnoses *why* revenue is at risk based on issuer error codes and telemetry logs.
- **Inputs**: `OpportunityID`, `PaymentID`, `PaymentAttempt` logs, issuer error messages.
- **Outputs**: `primary_root_cause`, `root_cause_explanation`, `is_transient`, `confidence_score`.

### 4.2 Agent 2: Recovery Planner Agent
- **Purpose**: Ranks candidate recovery interventions and estimates Expected Recovery Value ($EV$).
- **Inputs**: Root Cause output, Payment & Customer context, allowed merchant interventions.
- **Outputs**: `recommended_action_type`, `action_parameters`, `expected_recovery_value`, `agent_confidence`.

### 4.3 Agent 3: Verification Agent
- **Purpose**: Validates whether executed actions converted target transactions into captured funds based on event log evidence.
- **Inputs**: Executed `RecoveryAction` details, reconstructed payment/order state.
- **Outputs**: `is_verified_recovered`, `verified_amount`, `attribution_type`, `verification_reasoning`.
