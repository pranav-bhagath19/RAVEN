# RAVEN Agent Architecture Specification

## 1. Overview & Agent Boundaries

RAVEN uses a focused, multi-agent architecture comprising **exactly three specialized AI agents**. 

Agents operate strictly within bounded semantic reasoning roles. They do **not** execute direct side-effects, alter monetary figures, or bypass policy checks. All actions generated by agents are submitted as structured candidates to the **Deterministic Policy Engine**.

```
                           ┌──────────────────────────┐
                           │ Root Cause Analyst Agent │
                           └────────────┬─────────────┘
                                        │ Diagnosis & Context
                                        ▼
                           ┌──────────────────────────┐
                           │ Recovery Planner Agent   │
                           └────────────┬─────────────┘
                                        │ Candidate Action + Confidence
                                        ▼
                          [ Deterministic Policy Engine ]
                                        │ Approved Action Executed
                                        ▼
                           ┌──────────────────────────┐
                           │ Verification Agent       │
                           └──────────────────────────┘
```

---

## 2. Agent 1: Root Cause Analyst Agent

### Purpose
Analyzes failed transactions, issuer error responses, historical customer behavior, and network telemetry to determine *why* revenue is at risk.

### Inputs
- `OpportunityID` & associated `PaymentID`
- Historical `PaymentAttempt` records
- Issuer/Gateway error codes and raw gateway messages
- Customer transaction history (`get_payment_history`)
- Recent failure pattern statistics (`get_failure_patterns`)

### Outputs
- `primary_root_cause`: `Enum` (`TRANSIENT_ISSUER_DOWNTIME`, `INSUFFICIENT_FUNDS`, `EXPIRED_CARD`, `AUTHENTICATION_ABANDONMENT`, `INVALID_UPI_PIN`, `GATEWAY_TIMEOUT`)
- `root_cause_explanation`: `String` (Structured textual explanation for audit dashboard)
- `is_transient`: `Boolean`
- `confidence_score`: `Float` (`0.0` to `1.0`)

### Tools Available
- `get_payment`
- `get_payment_history`
- `get_event_history`
- `get_failure_patterns`

### Constraints & Failure Modes
- **Constraint**: Cannot recommend recovery actions or execute side-effects.
- **Failure Mode**: If telemetry data is inconclusive or error logs are blank, agent must set `confidence_score < 0.50` and mark cause as `UNKNOWN_REQUIRES_VERIFICATION`.

---

## 3. Agent 2: Recovery Planner Agent

### Purpose
Generates candidate recovery interventions (e.g., smart retry schedule, payment link dispatch via WhatsApp/Email, fallback payment method request), ranks options by Expected Recovery Value (\(EV\)), and selects the optimal bounded action.

### Mathematical Formulation
$$\text{Expected Recovery Value } (EV) = P(\text{success} \mid \text{context}) \times \text{Transaction Value (paise)} - \text{Intervention Cost (paise)}$$

### Inputs
- Root Cause Analysis output (`primary_root_cause`, `is_transient`, `confidence_score`)
- Payment & Customer context (`get_customer`, `get_revenue_risk`)
- Allowed Merchant Interventions (`get_allowed_interventions`)

### Outputs
- `recommended_action_type`: `Enum` (`SMART_RETRY`, `PAYMENT_LINK_DISPATCH`, `FALLBACK_CHANNEL_NOTIFY`, `ESCALATE_TO_HUMAN`)
- `action_parameters`: `JSON` (e.g., `retry_delay_seconds: 1800`, `channel: "WHATSAPP"`)
- `expected_recovery_value_paise`: `Integer`
- `agent_confidence`: `Float` (`0.0` to `1.0`)
- `reasoning_summary`: `String`

### Tools Available
- `get_revenue_risk`
- `get_allowed_interventions`
- `calculate_expected_recovery`

### Constraints & Failure Modes
- **Constraint**: Must select ONLY from merchant-approved intervention types returned by `get_allowed_interventions`. Cannot execute side-effects directly.
- **Failure Mode**: If `agent_confidence < 0.70` or transaction value exceeds high-value thresholds, agent must output `recommended_action_type = ESCALATE_TO_HUMAN`.

---

## 4. Agent 3: Verification Agent

### Purpose
Performs deterministic post-intervention auditing to verify whether a executed recovery action resulted in genuine captured revenue.

### Inputs
- Executed `RecoveryAction` details
- Current payment/order state derived from Event Replay Engine (`verify_payment_state`, `verify_recovery`)

### Outputs
- `is_verified_recovered`: `Boolean`
- `verified_amount_paise`: `Integer`
- `attribution_type`: `Enum` (`DIRECT_ACTION_ATTRIBUTION`, `ORGANIC_CUSTOMER_RETRY`, `UNRECOVERED`)
- `verification_reasoning`: `String`

### Tools Available
- `verify_payment_state`
- `verify_recovery`
- `record_audit_event`

### Constraints & Failure Modes
- **Constraint**: Must rely strictly on verified event replay logs. Cannot assume an action succeeded without `payment.captured` or `order.paid` event evidence.
- **Failure Mode**: If state is ambiguous or gateway API returns `PENDING`, agent flags outcome as `UNVERIFIED_PENDING_POLL` and schedules follow-up check.

---

## 5. Confidence Thresholds & Human Escalation Matrix

| Confidence Score | Recovery Planner Output | Policy Action |
| :--- | :--- | :--- |
| **\(\ge 0.85\)** | Direct Recovery Action (e.g., Smart Retry) | Auto-Approve (if policy checks pass) |
| **\(0.70 - 0.84\)** | Bounded Communication (e.g., Payment Link) | Auto-Approve (if within contact limits) |
| **\(< 0.70\)** | `ESCALATE_TO_HUMAN` | Route to Merchant Operations Dashboard |
